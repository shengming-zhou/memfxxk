# T17 · 用户优先级驱动的自适应上下文装载

依赖：T16 的 P0–P9 全部完成。本任务**不修改** T16 任何阶段的范围，阶段编号从 P10 接着往下排。先读 `AGENTS.md`、`docs/architecture.md`、T16 委托书，以及 T16 各阶段的交付说明。

## 背景

第一个真实使用场景是写长篇、强设定的小说。这个场景里信息天然有层级：世界观设定不能违反，但往往很长；正文也重要，但越早的章节越不需要原文；还有角色卡、地点、势力、草稿、灵感等等。全部塞进上下文太贵，只按关键词触发、整条带或整条砍（SillyTavern 的 Lorebook / World Info 就是这种做法），在长篇里又会漏掉关键设定。

用户不想给每类内容规定固定的含义。用户只想**给内容一个整数优先级**，其余的交给系统：维护内容、决定这次带什么、带多详细，并且根据使用情况慢慢调整。

现在的 `build_context` 用的是固定分区（documents、pinned、working、evidence 各有固定额度），某个分区用不完的额度不能给别的分区。这正是本任务要替换的部分。

## 设计原则

1. **优先级只是一个整数，没有固定含义。** 系统只用它的大小关系，不能在代码里假设"最高级是铁律""最低级是草稿"之类的语义。优先级相同的内容自然成为一层，有几种不同的数值就有几层。
2. **按比例分配，用不完的往下流。** 层越靠前权重越大，但不能独占预算；每个非空的层都有保底。
3. **超预算时先降级，再舍弃。** 每条内容有几个不同详细程度的版本，预算紧时用粗一些的版本，而不是整条扔掉。
4. **分配规则可以调整，但每次只调一点。** 根据使用中的信号慢慢调整，行为要稳定，不能来回震荡。
5. **算法做底，LLM 做可选微调。** 不配 LLM 时整套机制照样能跑，结果是确定的；配了 LLM 时，它只能在算法划定的范围内调整。
6. AGENTS.md 的硬性规则全部有效。特别是：多详细程度版本是派生物，必须能从原文重建，写回前校验 `generation`；bundle 只存引用，不存内容。

### P10 · 任意整数优先级与继承

- 优先级改为任意整数，去掉 1–5 的约束（新迁移，可降级；降级时把超出范围的值截到 1–5，并在迁移说明里写清楚）。
- 优先级可以设在三个层级上：**文档目录**（路径前缀）、**文档或记录**、**文档内的章节**。子级没设的继承父级，设了的覆盖父级。没有任何设置时用项目默认值。
- 新的 API、SDK、MCP 工具：设置、查看、清除优先级；查看某条内容的"生效优先级"以及它是从哪里继承来的。
- 分层函数：给定一组候选，按生效优先级的不同取值分层，并按从高到低排序。

**验收**：继承和覆盖的组合都有测试；作用域隔离（另一个 user/project 的优先级设置不生效）；旧数据迁移后行为不变。

### P11 · 多详细程度版本

每条可装载的内容维护三个版本：

| 版本 | 用途 | 大致长度 |
|---|---|---|
| `full` | 原文 | 原长 |
| `summary` | 核心内容和主要限制 | 原文的 10%–20%，有上限 |
| `line` | 一句话说明它是什么 | 一两句 |

- 适用于文档章节（按标题切出的块）、`note`、`fact`、`lesson`、记忆块，以及 T16 新增的可装载类型。`turn` 记录和正文章节的摘要可以复用 T16 P1 的压缩结果。
- 新的 LLM 任务 `resolution_summarize`，按 T16 的提示词标准编写。`summary` 和 `line` 不能引入原文里没有的内容。
- 原文改动后，后台作业重新生成，写回前校验 `generation`。没配模型时，`summary` 和 `line` 用确定性的截断生成，并标记为降级版本。
- 原文删除后，所有版本跟着删除。

**验收**：生成、重建、降级标记、删除传播、作用域隔离都有测试；在 fake LLM 下，修改文档后旧版本不会被装载。

### P12 · 自适应分配器

在 `build_context` 里新增 `allocator=adaptive`，现有的固定分区保留为 `allocator=fixed`。在 P15 的评测结果出来之前，默认仍然是 `fixed`。

**第一步：收集候选。** 所有来源（文档章节、记忆、近期对话、检索证据、图证据、T16 的各策略产物）的候选统一进入一个池子。每个候选有生效优先级、相关度分数、三个版本各自的 token 数。

**第二步：估算每层的需求。** 每层的需求 = 这一层里相关候选的 `line` 版本 token 数之和，再加上把最相关的若干条展开成 `summary` 或 `full` 所需的量（上限可配）。

**第三步：注水分配。**

1. 每层按排名得到一个权重。默认按几何衰减（衰减系数可配），也可以由 P13 学出来的权重替代。
2. 按权重把总预算分给各层。
3. 分到的额度超过需求的层，把多出来的部分按权重重新分给还不够的层，重复到稳定为止。
4. 每个非空层有保底：至少能放下它最相关的若干条候选的 `line` 版本。保底的总和超过预算时，从最低层开始减少保底条数，并在 bundle 里记录。

**第四步：在层内装填。** 先放所有入选候选的 `line` 版本，再按"边际价值 ÷ 增加的 token"贪心升级为 `summary`，然后是 `full`。边际价值由相关度和优先级共同决定：在同一层里先看相关度；跨层比较时，相关度明显低的高优先级候选不能挤掉相关度高的低优先级候选。阈值可配，并写进开发手册。

**第五步：修补"差一点放不下"。** 某个候选的下一级版本只差一点点（差额小于可配的比例）就能放下时，按顺序尝试：

1. 把同层或更低层里价值最低的一条降一级，腾出空间；
2. 使用全局机动额度（默认总预算的 3%）；
3. 在段落或小标题处截断，并标注可以用 `memory_get` 查看全文。

**第六步：排列顺序。** 最高层的内容固定放在最前面，顺序在请求之间保持不变，以便利用模型服务商的前缀缓存。动态变化的部分放在后面。

**可选的 LLM 微调**（任务名 `context_plan`）：输入是本次查询或写作任务的简短描述，加上各层的名称示例和当前权重；输出是各层权重的调整系数。代码把系数限制在可配范围内（默认 0.7–1.3），超出就截断。LLM 调用失败时直接用算法结果，不报错。

**bundle 记录**：每层分到的额度、实际用量、每个候选用了哪个版本、被降级或舍弃的原因、修补步骤做了什么、LLM 微调的输入和输出系数（只记系数和 `llm_calls` 的 ID）。

**验收**：

- 确定性单测覆盖：注水重新分配、保底、保底超预算、层内升级顺序、修补的三种手段、跨层相关度保护、顺序稳定。
- 总用量不超过预算，包括 T16 P1 的内存压力信号在新分配器下仍然正确。
- 新旧分配器使用同一份候选时，bundle 都能解释每条候选的去向。

### P13 · 反馈学习

每个项目维护一份分配状态：各层权重、衰减系数、展开上限，存在新表里并带版本。

收集四类信号：

| 信号 | 判定方式 | 调整方向 |
|---|---|---|
| 漏了 | 同一轮里，模型调用 `memory_get` 或 `memory_search` 取回了本次 bundle 舍弃或降级的内容 | 提高该候选所在层的权重 |
| 白带了 | 带进去的 `summary` 或 `full` 内容，在模型回复里没有被引用或用到（先用引用 ID 和文本重合度判定，可选用 LLM 判定） | 略降该层权重 |
| 写崩了 | P14 一致性检查发现违反了某条内容，而这条内容本次被降级或舍弃 | 较大幅度提高该层权重 |
| 用户更正 | 用户修改了模型的输出，涉及的内容能对应到具体候选 | 按涉及的候选调整 |

- 调整用滑动平均，每次的步长很小，并设上下限，保证不会震荡。
- 提供查看当前分配状态、查看调整历史、重置为默认的 API 和 CLI。
- 调整历史可回放：给定同一份信号序列，得到相同的状态。

**验收**：四类信号各有测试；步长和上下限生效；重置有效；作用域隔离；用一段模拟的信号序列验证权重收敛而不是来回震荡。

### P14 · 长篇小说场景

这些功能面向写小说，但都按通用能力实现，不依赖固定的内容分类：

- **关键词和别名触发。** 新的候选来源：从内容里自动提取名称、别名和关键词（可复用 T16 P3 的实体抽取），正文或查询里出现时，把对应内容加入候选池。用户可以手动补充关键词。这是 Lorebook 的做法，但这里只是候选来源之一，最终带不带、带多详细，由 P12 的分配器决定。
- **一致性检查。** 新的 API、SDK、MCP 工具：输入一段新写的文字，以及一个优先级下限（默认为项目里最高的两层）。系统找出和这段文字相关、且优先级不低于下限的内容，由 LLM（任务名 `consistency_check`）列出可能的冲突，每条冲突带原文位置和对应内容的 ID。**只报告，不修改任何内容。**
- **故事内时间。** 事实和图的边除了现有的时间字段，可以额外带"故事内时间"（字符串加可排序的键，由用户或抽取结果提供）。查询时可以按故事内时间过滤，用来回答"这个时间点某角色知道什么、是什么状态"。倒叙和插叙时，写作顺序和故事内时间可以不同。
- **分层正文摘要。** 章节摘要、卷摘要，复用 T16 P1 的压缩和 P11 的多版本，作为正文内容的 `summary` 和 `line` 版本。

**验收**：关键词触发、别名、一致性检查（含没有冲突时返回空列表、故意制造的冲突能被找到）、故事内时间过滤都有测试。

### P15 · 评测

用户会提供一部自己的小说的设定和章节作为测试材料。在此之前，先用一份公版小说或自造的设定集把流程跑通。

- **测试题**：设定问答题（例如"第三章主角用的什么武器""某势力和某势力是什么关系"），以及故意违反设定的文段检测题。题目和答案标注格式写进开发手册，方便用户自己加题。
- **对照组**，统一使用同一个预算：
  1. Lorebook 式：关键词触发，整条带或整条砍，按优先级排序截断。
  2. 固定分区：现有的 `allocator=fixed`。
  3. 自适应分配：`allocator=adaptive`，不开 LLM 微调。
  4. 自适应分配加 LLM 微调。
  5. 自适应分配加反馈学习，用一段写作过程回放产生的信号预热后再测。
  6. 不限预算全部装载，作为上限参照。
- **报告**：设定问答正确率、冲突检出率、每次请求的 token 数和其中可被前缀缓存的比例、延时。结果写到 `eval/results/t17/`，带清单。
- 写一份大白话的结论页，说明自适应分配是否值得设为默认，并据此调整默认配置，决定记到 `docs/decisions/`。
